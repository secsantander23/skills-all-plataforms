# Token pipeline reference

Read `../SKILL.md` first. This file covers how to keep design and code tokens in sync,
how to structure a token source, and how to check token sets automatically.

## Source of truth

Pick one and say so loudly:

| Source | Best when | Cost |
| --- | --- | --- |
| JSON token file in the repo | Code and design both derive from it; engineers own changes | Designers must edit JSON or use a plugin |
| Figma variables | Design is the source; a plugin exports JSON for code | Requires a sync step and a review policy |
| Platform code | A library published to npm and consumed by design tools | Slowest loop; designers see changes late |

Whatever you choose, the flow is one-way:

```
source of truth  ->  build  ->  CSS / TypeScript / iOS / Android / docs
```

Never allow hand edits in generated outputs. Generated files get a header comment
saying so, and CI regenerates them and fails on a diff.

## Token file structure

The Design Tokens Community Group format uses `$value`, `$type`, `$description`, and
`$extensions`, with `{path.to.token}` references.

```json
{
  "color": {
    "$type": "color",
    "blue": {
      "600": { "$value": "#1d4ed8" },
      "700": { "$value": "#1e40af" }
    }
  },
  "space": {
    "$type": "dimension",
    "2": { "$value": "0.5rem" },
    "4": { "$value": "1rem" }
  },
  "semantic": {
    "color": {
      "action": {
        "$value": "{color.blue.600}",
        "$description": "Interactive accent. 4.5:1 minimum against {semantic.color.surface}."
      },
      "surface": {
        "$value": "#ffffff",
        "$description": "Base surface for cards and page background."
      },
      "text": {
        "$value": "#0f172a",
        "$description": "Body text. 4.5:1 minimum against {semantic.color.surface}."
      },
      "text-muted": {
        "$value": "#475569",
        "$description": "Secondary text. 4.5:1 minimum against {semantic.color.surface}."
      },
      "focus-ring": {
        "$value": "{color.blue.600}",
        "$description": "Focus indicator. 3:1 minimum against adjacent colors (WCAG 1.4.11)."
      }
    },
    "space": {
      "gap": { "$value": "{space.4}" },
      "inset": { "$value": "{space.4}" }
    }
  }
}
```

Note the `$type` inheritance: setting `$type` on a group applies to its members, so you
do not repeat it on every leaf.

## Naming conventions

| Token | Convention | Example |
| --- | --- | --- |
| Primitive color | `hue-step` | `blue-600` |
| Primitive dimension | `scale-step` | `space-4`, `radius-md` |
| Semantic color | `role` | `color-action`, `color-text-muted` |
| Semantic dimension | `role` | `space-gap`, `space-inset` |
| Component token | `component-part-role` | `button-padding-inline`, `button-label-color` |

Avoid:

- Names describing appearance at the semantic tier (`color-blue-action`).
- Names describing a single screen (`color-sidebar-bg`).
- Encoded values in names (`color-ds-new-blue`).

## Generating CSS

A generation script should be deterministic and checked in:

```ts
// scripts/build-tokens.ts
import { readFileSync, writeFileSync } from 'node:fs';

type TokenNode = { $value?: string; $type?: string; [key: string]: unknown };

const source = JSON.parse(
  readFileSync('tokens/semantic.tokens.json', 'utf8'),
) as Record<string, TokenNode>;

function flatten(node: Record<string, TokenNode>, path: string[] = []): Map<string, string> {
  const out = new Map<string, string>();
  for (const [key, value] of Object.entries(node)) {
    if (key.startsWith('$')) continue;
    const next = [...path, key];
    if (typeof value.$value === 'string') {
      out.set(next.join('-'), value.$value);
    } else {
      for (const [k, v] of flatten(value as Record<string, TokenNode>, next)) out.set(k, v);
    }
  }
  return out;
}

const tokens = flatten(source);
const css = [
  '/* Generated by scripts/build-tokens.ts. Do not edit. */',
  ':root {',
  ...[...tokens].map(([name, value]) => `  --ds-${name}: ${value};`),
  '}',
  '',
].join('\n');

writeFileSync('src/styles/generated/tokens.css', css);
```

Production generators should do more: resolve `{a.b.c}` references, apply a naming
prefix, emit separate themes, and emit TypeScript constants. Style Dictionary does this
out of the box; if you write your own, cover reference resolution and aliasing, since
those are where hand-rolled generators break.

## Aliasing and references

- **Alias once.** If a semantic token references another semantic token, the second-level
  indirection makes the graph hard to reason about. One hop is usually enough.
- **Never alias to a screen.** `--color-header-bg` referencing `--color-surface` is
  fine; `--color-header-bg` being defined separately is duplication.
- **Circular references** are a generator error, not a runtime surprise. Fail the build.

## Multiple themes in one output

```css
:root { --ds-color-surface: #ffffff; --ds-color-text: #0f172a; }

[data-theme='dark'] { --ds-color-surface: #0f172a; --ds-color-text: #f8fafc; }

[data-theme='high-contrast'] {
  --ds-color-surface: #000000;
  --ds-color-text: #ffffff;
}
```

Emit one block per theme from a single token file where the semantic layer is the only
thing that varies. If a theme changes a primitive too, that is a signal the theme is
really a second brand and probably wants its own semantic file.

## Contrast checking in CI

Contrast is a constraint you can automate. Write a checker that walks the semantic
tokens, resolves aliases, and compares every declared foreground/background pair.

```ts
type Rgb = { r: number; g: number; b: number };

function parseHex(hex: string): Rgb {
  const h = hex.replace('#', '');
  const full = h.length === 3 ? h.split('').map((c) => c + c).join('') : h;
  return {
    r: parseInt(full.slice(0, 2), 16) / 255,
    g: parseInt(full.slice(2, 4), 16) / 255,
    b: parseInt(full.slice(4, 6), 16) / 255,
  };
}

function relativeLuminance({ r, g, b }: Rgb): number {
  const lin = (c: number) => (c <= 0.04045 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4);
  return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b);
}

function contrastRatio(a: string, b: string): number {
  const la = relativeLuminance(parseHex(a));
  const lb = relativeLuminance(parseHex(b));
  const [hi, lo] = la > lb ? [la, lb] : [lb, la];
  return (hi + 0.05) / (lo + 0.05);
}

const textOnSurface = contrastRatio('#0f172a', '#ffffff');
if (textOnSurface < 4.5) {
  throw new Error(`text/surface contrast ${textOnSurface.toFixed(2)} is below 4.5`);
}
```

Extend this to a real token walk, cover every theme, and include non-text pairs: focus
rings and control borders need 3:1 against adjacent colors (WCAG 1.4.11). The formulas
are from WCAG's relative luminance definition; verify them against the specification at
https://www.w3.org/TR/WCAG22/.

## Tooling verification

Token tooling changes quickly and configuration keys differ between tools. Before
adopting a tool:

1. Read its official documentation for the input format it accepts.
2. Confirm it reads the Design Tokens Community Group format, or that you maintain a
   converter.
3. Confirm the outputs you need: CSS custom properties, TypeScript, and your mobile
   platforms.
4. Run it in a branch and inspect the generated output before trusting it in a pipeline.

Relevant documentation:

- Design Tokens Community Group format:
  https://www.designtokens.org/tr/drafts/format/
- Style Dictionary: https://styledictionary.com/
- Tokens Studio: https://tokens.studio/

## Failure modes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Generated file drifts from the token source | Generated output committed by hand | Header comment plus CI regeneration check |
| A theme silently loses a token | New semantic token added in one theme only | Generate all themes from one file and fail on missing keys |
| Contrast fails in dark mode only | Dark theme values added without a contrast check | Run the checker across every theme |
| A token rename breaks every product | No codemod and no deprecation | Alias old name, deprecate, publish a codemod |
| Circular alias | Two semantic tokens referencing each other | Fail the build on cycles |

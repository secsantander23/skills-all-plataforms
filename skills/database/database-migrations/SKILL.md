# Database Migrations

A migration is a program that runs while other people are using the database. The whole
discipline is about making the new schema and the old application version both work at the
same moment, and never holding a lock long enough to be noticed.

## When to use this

- Any change to a table that already has traffic.
- Renaming or retyping a column, adding `NOT NULL` to a populated column, adding a foreign key,
  or creating an index on a large table.
- Choosing between migration tools, or setting one up for the first time.
- Writing a backfill for millions of rows.
- Deciding what "rollback" means when the change is not reversible.
- Reviewing someone else's migration before it ships.

## The one rule

**The schema at any instant must be compatible with both the old and the new version of the
application.** Deploys are not atomic: the old code keeps serving traffic while new pods warm
up, and a rollback can happen minutes after you migrate.

If you violate that rule, you get errors like
`column "new_name" does not exist` from the still-running old version, or `relation
"orders_v2" does not exist` from a pod that has not restarted yet.

## Quick start

Renaming a column on a live table, done in six deploys instead of one statement.

```sql
-- Migration 1: expand. Adds the new column. Fast, no table rewrite.
ALTER TABLE orders
    ADD COLUMN customer_email text;

-- Deploy: application writes BOTH customer_email and customer_id.

-- Migration 2: backfill, in batches, run as a job not as a migration.
-- (see the batched UPDATE recipe below)

-- Deploy: application reads customer_email, falls back to customer_id if NULL.

-- Migration 3: enforce.
ALTER TABLE orders
    ADD CONSTRAINT orders_customer_email_not_null
        CHECK (customer_email IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_email_not_null;

-- Deploy: remove the fallback read path.

-- Migration 4: contract, later, when nothing reads the old column.
ALTER TABLE orders DROP COLUMN customer_id;
```

Each step is independently safe, independently reversible, and never holds a long lock.

## Migration tooling

| Tool | Style | Notes |
| --- | --- | --- |
| Plain SQL scripts | Versioned files | Full control. You own the transaction semantics and the lock behaviour. |
| Flyway | Versioned SQL, or Java migrations | Naming convention `V<version>__<description>.sql` for versioned, `R__<description>.sql` for repeatable. Has a checksum-based drift check. |
| Liquibase | Changelog in XML, YAML, JSON, or formatted SQL | Changelogs can reference changesets per environment. Strong for regulated environments that need formal change records. |
| Atlas | Declarative schema written in HCL, diffed against the database | Schema-as-code, drift detection, and a linting step for destructive changes. |
| Alembic | Python, for SQLAlchemy projects | `alembic revision -m "..."`, then hand-edit `upgrade()` and `downgrade()`. Autogenerate produces a starting point, not a finished migration. |
| Prisma | Generated from the Prisma schema, plus hand-edited SQL | `prisma migrate dev` in development, `prisma migrate deploy` in production. Data migrations and complex DDL still need hand-written SQL. |
| Django | Python files, `makemigrations` then `migrate` | `RunPython` for data migrations. Always review autogenerated files. |
| Rails | Ruby, timestamps in filenames | `rails db:migrate`, `rails db:rollback`. |
| Knex | JavaScript, timestamped files | `knex migrate:latest`, `knex migrate:rollback`. |
| gh-ost / pt-online-schema-change | Online schema change for MySQL | They build a shadow table, copy data, and swap. Slower than native DDL but avoids long locks on engines where DDL is not instant. |

Whatever you choose, keep migrations in version control, run them in CI against a database
cloned from production shape, and never edit a migration that has been applied anywhere.

## Zero-downtime DDL, statement by statement

Know which statements are cheap and which are not. The class of operation matters more than
the exact version, but verify against your engine's documentation.

| Operation | Cost | Safe online? |
| --- | --- | --- |
| `ADD COLUMN` with a constant default | Metadata only in recent PostgreSQL | Yes |
| `ADD COLUMN` with a volatile default, or no default | Table rewrite | Rarely |
| `ADD COLUMN ... NULL` | Metadata only | Yes |
| `DROP COLUMN` | Metadata only in recent PostgreSQL | Yes (breaks old code, see the rule above) |
| `SET NOT NULL` | Full table scan unless a valid `CHECK` proves it | Use the two-step `CHECK` approach |
| `DROP NOT NULL` | Metadata only | Yes |
| `SET DEFAULT` | Metadata only | Yes |
| Type change that rewrites (for example widening `varchar`, many `numeric` scale changes) | Full table rewrite with `ACCESS EXCLUSIVE` | No |
| Type change that is binary-coercible and does not rewrite (for example some `varchar` to `text` cases) | Metadata only | Yes |
| `CREATE INDEX` | Exclusive to writes for the duration | Use `CONCURRENTLY` |
| `ADD FOREIGN KEY` validated | Scans both tables under a strong lock | Add `NOT VALID`, then `VALIDATE CONSTRAINT` |
| `ADD CHECK` validated | Scans the table | Add `NOT VALID`, then `VALIDATE CONSTRAINT` |
| `ALTER COLUMN TYPE ... USING expr` | Rewrite plus a full expression evaluation | Add a new column instead |
| `RENAME COLUMN` / `RENAME TABLE` | Fast, but breaks running code | Expand-contract |

### Add NOT NULL without a rewrite

```sql
-- Step 1: add the check without validating it. Fast, takes a brief lock.
ALTER TABLE orders
    ADD CONSTRAINT orders_email_present
        CHECK (email IS NOT NULL) NOT VALID;

-- Step 2: validate with a scan that does not block reads or writes.
ALTER TABLE orders VALIDATE CONSTRAINT orders_email_present;

-- Step 3: now SET NOT NULL can use the validated check as proof in recent PostgreSQL.
ALTER TABLE orders ALTER COLUMN email SET NOT NULL;

-- Optional, if you never want to accept NULL even briefly:
-- ALTER TABLE orders ALTER COLUMN email SET NOT NULL;  -- do this instead of steps 1-3
--     when the table is small or you can tolerate the scan.
```

### Add a foreign key without a long lock

```sql
ALTER TABLE orders
    ADD CONSTRAINT orders_customer_fk
        FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;

ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;
```

`VALIDATE CONSTRAINT` takes a weaker lock than the initial add, so it does not block normal
reads and writes while it scans.

### Create an index without blocking writes

```sql
CREATE INDEX CONCURRENTLY orders_customer_created_idx ON orders (customer_id, created_at);
```

- Cannot run inside a transaction block. Configure your migration tool to allow non-transactional
  statements.
- Takes two table scans and waits for existing transactions, so it is slow and can wait a long
  time.
- On failure it leaves an invalid index that the planner ignores. Clean up with
  `DROP INDEX CONCURRENTLY orders_customer_created_idx;` and retry.
- Drop with `DROP INDEX CONCURRENTLY`.

## Lock hazards

The dangerous property of PostgreSQL (and other engines with similar locking) is not that a
DDL statement takes a lock. It is that a blocked lock request **queues** and blocks every
later request behind it. An `ALTER TABLE` waiting on one long transaction turns every
subsequent read into a read that also waits. That is how a five-second migration becomes a
forty-minute outage.

Defenses:

```sql
-- In every migration, before the DDL.
SET lock_timeout = '3s';
SET statement_timeout = '0';   -- the backfill may legitimately take a long time

ALTER TABLE orders ADD COLUMN shipped_at timestamptz;
```

If the `lock_timeout` fires you get an error instead of a queue. Retry the migration later or
during a quiet window.

Additional rules:

- Retry `lock_timeout` failures with jittered backoff, never in a tight loop.
- Never run DDL while holding an open application transaction.
- Set `lock_timeout` and `statement_timeout` per migration session, not globally, so you do not
  change application behaviour.
- On engines where `NOWAIT`-style lock acquisition is available, use it in tooling.
- For the highest-risk statements (large table rewrite, big backfill), take the change outside
  peak hours and with a rollback prepared.

## Backfilling large tables safely

A single `UPDATE` over fifty million rows holds locks for its entire duration, generates a huge
amount of WAL, bloats the table, and can replicate badly enough to stall replicas.

Batch it:

```sql
-- Repeat until zero rows are affected. Each statement is its own transaction.
UPDATE orders
SET shipped_at = created_at
WHERE shipped_at IS NULL
  AND id BETWEEN $1 AND $2;   -- $2 is a window over the primary key

-- Between batches, in the same script:
SELECT pg_sleep(0.1);  -- throttle so application traffic and replication keep up
```

A robust driver script:

```bash
#!/usr/bin/env bash
# Backfill shipped_at in primary-key windows.
set -euo pipefail

psql -v ON_ERROR_STOP=1 -d "$DATABASE_URL" <<'SQL'
SELECT min(id) AS lo, max(id) AS hi FROM orders;
SQL

read -r LO HI < <(psql -At -d "$DATABASE_URL" \
  -c "SELECT min(id)||' '||max(id) FROM orders")

BATCH="${BATCH_SIZE:-50000}"
START=$LO
while [ "$START" -le "$HI" ]; do
  END=$(( START + BATCH - 1 ))
  echo "backfilling $START..$END"
  psql -v ON_ERROR_STOP=1 -d "$DATABASE_URL" \
    -c "SET lock_timeout='5s';
         UPDATE orders
         SET shipped_at = created_at
         WHERE shipped_at IS NULL AND id BETWEEN ${START} AND ${END};"
  START=$(( END + 1 ))
  psql -d "$DATABASE_URL" -c "SELECT pg_sleep(0.2);"
done
```

Guidance:

- **Batch by primary key**, not by `OFFSET`. `OFFSET` re-scans and slows down as the batch
  advances.
- **Keep each batch well under the old transaction timeout** on replicas so lag stays bounded.
- **Throttle** between batches. Sleep values are workload-specific; measure.
- **Watch replication lag and replication errors** throughout.
- **Commit between batches.** A single giant transaction defeats the entire exercise.
- **Make it idempotent and resumable.** `WHERE shipped_at IS NULL` plus a key window means you
  can stop and restart at any point.
- **Do not run the backfill inside the migration tool.** Migrations should be fast, auditable
  DDL. Long data movement belongs in a job or a one-off script, tracked separately.
- **Watch disk and WAL volume.** Backfills inflate the table and generate WAL; confirm headroom
  before starting.
- **Vacuum afterwards.** The batched update leaves dead tuples behind.

## Rollback strategy

Two different questions, often conflated:

1. **Can I undo this?** Some changes are not reversible: `DROP COLUMN` destroys data, a type
   change may lose precision, a bad backfill overwrote values. For those, the rollback is a
   forward fix or a restore from backup.
2. **Should I roll back?** Even a reversible migration may be wrong to undo if the application
   has already written new-shape data.

Practical rules:

- Ship a `down` migration where reversal is genuinely possible and cheap. Otherwise write a
  comment saying so explicitly.
- Prefer **roll forward**. A new migration that fixes the problem is safer than reverting a
  migration that production has already built on.
- Test the down path in CI. An untested down migration is a fiction.
- Never make the down migration destructive without saying so, for example
  `DROP COLUMN` in a `downgrade()`.
- Before any irreversible change, confirm backups and point-in-time recovery are configured
  and *tested*. A backup you have never restored is not a backup.
- For data migrations, snapshot the affected rows into a restore table in the same migration.
  That makes the down path a set-based copy back.

```python
# Alembic: explicit down when possible, honest comment when not.
def upgrade():
    op.add_column("orders", sa.Column("shipped_at", sa.TIMESTAMP(timezone=True)))

def downgrade():
    # Data in shipped_at is lost on downgrade. Deploy order makes this safe:
    # no running code reads shipped_at before this migration is applied.
    op.drop_column("orders", "shipped_at")
```

## Migration review checklist

Before approving any migration against a table with traffic:

- [ ] Does the change keep the old application version working? Check every column it drops or
      renames, every constraint it adds, and every table it touches.
- [ ] Which statement takes the longest lock? Does it have a `lock_timeout`?
- [ ] Is any statement a full table rewrite? If so, is there an expand-contract alternative?
- [ ] Is the index created with `CONCURRENTLY`, and is the migration tool configured to allow
      non-transactional statements?
- [ ] Are added foreign keys and checks added `NOT VALID` then validated separately?
- [ ] Is the data movement batched, committed per batch, resumable, and run outside the
      migration tool?
- [ ] Is the migration idempotent or at least safely re-runnable after a partial failure?
- [ ] Is there a down migration, and has it been tested?
- [ ] Does it lock at all on a table where a queue of blocked requests would cascade?
- [ ] Has it been run against a production-shaped dataset with timing recorded?
- [ ] Is the rollback plan written down, and does it require a code deploy too?
- [ ] Does the migration change a column that a view, trigger, generated column, or
      materialized view depends on?
- [ ] Are permissions, row-level security policies, and grants preserved?

## Common mistakes

- **Renaming a column in one migration.** The running old version immediately errors. Expand,
  dual write, switch, contract.
- **`CREATE INDEX` without `CONCURRENTLY` on a large table.** Holds a lock that blocks all
  writes for the whole build.
- **Adding a validated foreign key or `CHECK` in one statement.** Validates by scanning under a
  lock. Use `NOT VALID` plus `VALIDATE CONSTRAINT`.
- **A million-row backfill inside the migration transaction.** Long lock, huge WAL, replica lag,
  and a migration that blocks every other deploy.
- **No `lock_timeout` in DDL.** A blocked DDL queues and stalls everything behind it.
- **Editing an already-applied migration.** Environments diverge silently. Add a new migration.
- **A `downgrade()` that quietly drops data.** Reviewers assume it is safe.
- **Batching with `OFFSET`.** Each batch rescans the skipped rows, so it slows down as it
  progresses and eventually dominates runtime.
- **Trusting autogenerated migrations.** Autogenerate produces a plausible diff, not a safe
  plan. It will happily emit a table rewrite.
- **Mixing DDL and a long data migration.** You lose the ability to run the DDL during a quiet
  window and the ability to rerun the data job.

## Anti-patterns

- "Just stop the app for two minutes." It works until the app has zero-downtime requirements,
  and it trains people to schedule outages instead of designing migrations.
- A migration per column rename. Each is a deploy. Collapse related changes, but never at the
  cost of breaking compatibility.
- One giant migration that adds a table, backfills it, switches reads, and drops the old table.
  There is no safe point to roll back to and no way to pause.
- Relying on the database's `IF NOT EXISTS` guard to make a migration re-runnable. It does not
  cover half the statements you write, and it hides genuine drift.
- Testing migrations only on an empty database. Constraint validation, index build time, and
  lock behaviour only appear at production scale.
- Rolling back by running the down migration while the new application version is still
  deployed. That is the fastest way to produce `column does not exist` in production.
- Encoding business logic in migrations. A migration should move the schema forward; a data
  migration that needs to be correct and idempotent deserves its own tests and its own audit.
